The Wake Boundary

How an agent holds a conversation on a messaging channel — without a polling loop, without losing messages, and without paying while nothing happens.

Teams · Slack · WhatsApp · Telegram · email github.com/muthuishere/agent-conversations MIT

An agent cannot be pushed to

An agent session is a request/response process. It cannot hold a socket, and nothing can push into it. To notice an inbound message, something must invoke the agent again.

The naive answer is a loop inside the agent:

while true: check for messages; sleep 5

Three things are wrong with it, and each gets worse with scale.

  1. It costs a turn per tick. Tokens are spent in proportion to time, not to traffic. An idle channel bills the same as a busy one.
  2. It still misses messages. Anything arriving between ticks waits for the next one, and a reply that lands mid-turn is simply not seen.
  3. It cannot survive the session. Close the terminal and the listener is gone — silently, which is the worst way for a listener to die.

Every real design is about who does the invoking, and the answer is never “the agent”.

Separate receiving from waking from answering

They have different lifetimes, different costs, and different failure modes. Fusing any two of them produces a system that either loses messages or burns money.

This is the whole architecture. Everything below is a consequence of holding the three apart — and the boundary that matters most is the one between the daemon, which never thinks, and the agent, which only thinks.

The three concerns
ConcernOwnerLifetimeCost
Receivingdaemonforever, outlives every session~zero — no model

Receiving gets messages out of the channel durably; waking tells an agent something arrived; answering decides and replies.

The shape of it

One always-on daemon with no model in it, a journal on disk, and a tripwire that costs nothing until it fires. The agent appears only to answer, and only once per batch.

        │  CHANNEL   (Teams / Slack / WhatsApp / SMTP) │

Below the line: infrastructure, no judgement. Above it: policy, no transport.

The three wake mechanisms

There are only three ways to get an agent invoked when a message lands. A mature product implements at least two.

W1 / W2 / W3 compared
 MechanismWho invokesIdle costLatencySurvives session deathPortability
W1 Blocked process exits, runtime re-invokes the session the agent runtimezeroinstant noruntime-specific
W2 Daemon spawns a fresh headless agent per batch the daemonzerospawn time yesuniversal
W3 Keystroke injection into a live interactive session an external driverzero~1 s noterminal-specific

W1

Background task exits, runtime re-invokes

The agent arms a blocked child process and ends its turn. The process sits on the journal costing nothing; when a message lands it exits, and the runtime — noticing a watched task finished — invokes the session again.

Choose it for an attended session that should react now. It is the cheapest and the fastest path, and it is the one that dies with the terminal.

Verify empirically. Runtime documentation on background-task-exit wake contradicts itself; whether your runtime actually re-invokes is a matter of observation, not of reading.

W2

Daemon spawns a handler per batch

The daemon itself launches a fresh headless agent when a batch is ready, hands it the messages, and lets it exit. No session needs to exist beforehand; nothing needs to survive.

Choose it for anything unattended and always-on. It depends on no runtime behaviour beyond “can start a process”, so it works everywhere — and a stateless handler with a small toolset is the easiest thing to secure.

This is the portable floor. Build it first. If W2 does not work, you do not have a product.

W3

Keystroke injection into a live session

An external driver types into a terminal that already has an idle agent sitting at its prompt. Crude, and entirely dependent on the terminal.

Choose it to reach a human-shaped session that armed nothing — the case W1 and W2 cannot cover, because there is no tripwire and spawning a second agent would not reach the one you mean.

A niche bridge, not a foundation. Never the only mechanism.

The rule

W1 and W3 are optimizations over W2, not alternatives to it. Ship the universal mechanism, measure whether latency actually hurts, and only then add a runtime-specific one.

The canonical envelope

Every channel is flattened into one shape before anything above the daemon sees it. This normalization is what makes the agent portable: the adapter is the only channel-specific code in the system.

{
  "id": "…",
  "at": "2026-09-09T10:00:00Z",
  "from":   { "id": "…", "name": "…" },
  "text":   "plain text, always present",
  "html":   "original rich body, or null",
  "source": { "kind": "chat|channel|email",
              "conversationId": "…",
              "name": "#general | dm",
              "threadId": "…" },
  "replyToId": null,
  "mentionsMe": false,
  "raw": { }
}

Two fields carry disproportionate weight.

source.kind plus conversationId decide reply routing. A direct message goes back to that conversation; a channel message goes back as a threaded reply. Get it wrong and the platform returns success while the reply vanishes — the failure is completely silent. The fix is structural: make the reply API take a message id and route itself, and make an unknown id fail loudly.

raw is never discarded. You will eventually need a field you did not anticipate, and re-fetching it from the channel is rarely possible.

respond <messageId> "text"    # dm → that conversation
                              # channel → threaded reply

The agent supplies a message id. The tool decides the target. See INTERFACES.md for the full contract.

Six things that decide whether it works

The daemon is infrastructure — no model, no judgement, no product policy. Almost all of its difficulty is in six details, and each of them has a specific way of going wrong.

Cursor and acknowledgement are not the same thing

This is the single most common bug in this class of system. Conflate them and messages are either redelivered forever or dropped without trace.

 MeansAdvanced byIf you get it wrong
read cursordelivery positionthe daemon, whenever a consumer is handed a messagenever advanced → infinite redelivery
ackprocessed / handledthe consumer, explicitlyconflated with the cursor → redelivered forever, or silently dropped

Persist the cursor immediately after a successful hand-off, never before. And reading the journal to look around must not advance anything — reading is not consuming.

The journal is append-only, and written first

One log per listener, one message per line, written before any consumer sees it, never mutated by a read. This is what turns “a message arrived while the agent was thinking” into a non-event, and it is also the audit record of who asked for what. Retention and compaction are a separate concern; the log is the source of truth.

Immediately before the journal sits self-echo suppression, which is non-negotiable. Without it the agent replies, the daemon sees the reply, the agent is woken, and it replies again — an infinite loop that costs real money and spams a real channel. Suppress by identity (from.id == self.id, or a distinct bot identity for outbound), never by content matching. The subtle trap: a handler configured with a different identity than the daemon replies as someone the suppression does not recognise, and the loop reappears. Pin the handler’s identity to the daemon’s, explicitly.

Coalesce — deliver a batch, not a message

After the first message, wait a short window (200–800 ms) and hand over everything that lands. Five people typing at once become one agent invocation instead of five. This is the biggest cost lever in the design, and it improves answers too: the agent sees the whole room at once instead of reacting to fragments.

Adaptive backoff, with a hard snap back

Fixed-interval polling is either wasteful or slow. Tier it on recent activity instead.

StateInterval
message on the last pollactive — 15 s
quiet > 2 min60 s
quiet > 10 minidle — 5 min
any message arrivessnap straight back to active
Known trade — state it out loud

At the idle tier you cannot notice traffic sooner than the idle interval. The first message after a long silence pays full idle latency — precisely the moment a human is starting a conversation. Mitigate by lowering the idle interval while a consumer is attached, or by letting an attended consumer poll on its own.

Heartbeat, because the defining failure is silent deafness

The listener dies, the agent believes it is live, and nobody finds out until someone asks why they were ignored. Defend against it directly: the daemon writes {ts, pollCount, lastMessageAt, intervalMs, scope} every cycle, and health fails if that record is older than roughly three intervals.

A consumer must refuse to block against a stale heartbeat — return an error rather than wait forever on a corpse. Silence must never be mistaken for “no messages”, and an agent must never report “listening” from memory. Read the heartbeat.

One consumer per listener

Two consumers on one cursor race for messages and tear down each other’s state; one dies and nobody notices. Enforce a single consumer with a pid or lock file, a clear error on conflict, and an explicit takeover flag for the case where you really do mean it.

The test

If changing a product rule forces a change in the daemon, the split is wrong. Change who the agent answers by changing a filter — never by re-plumbing the transport.

What the skill actually contains

Operating discipline: never write a polling loop; arm one tripwire and be woken. A timeout is not an error — distinguish “nothing arrived” from “something broke” by exit code. Never claim to be listening without checking state. The tripwire must be the process the runtime watches, not a detached grandchild whose exit notifies nobody. One consumer. Re-arm once per wake, after answering, not on a timer.

And policy: the daemon delivers everything, the skill decides what matters — --from, --exclude-from, --match, --in, --mentions-me. Filters apply at delivery, never to the journal, so a filtered-out message is still on disk and still auditable.

Rules first, model second

Most traffic is status, help, ping, acknowledgements. A regex table answers those in milliseconds at zero cost; escalate only what genuinely needs reasoning. That is what makes “many users, fast” affordable — and it degrades gracefully, because a rule table still works when the model is down.

Inbound messages are untrusted input

This architecture actively invites the problem: it takes text written by anyone at all and feeds it to an agent holding real tools.

A message saying “summarise the CEO’s inbox” or “run the deploy script” is data, not an instruction.

  • A message can request; it can never authorize.
  • Sender identity is not authorization. Many channels let a display name be spoofed, and even a trustworthy channel only tells you who posted — not what they may command.
  • Give the handler a capability boundary. A message-driven agent should reach the channel and its own product surface. Not mail, not credentials, not an unrestricted shell.
  • Escalation must be narrow. Route unmatched questions to a model with a restricted toolset, not to a general-purpose agent with everything mounted.
  • Audit. The journal is the record of who asked for what. Never let a read destroy it.

The fresh-handler-per-batch design (W2) helps here as a side effect: a stateless handler with a small toolset is far easier to reason about than a long-lived agent quietly accumulating capability and context.

Failure modes to design against

The recurring theme is a listener that stays visibly healthy while the wake path is severed. Every one of these was observed in practice, not theorized.

Build order

This one really is a sequence. Each step depends on the one before it, and step four is where you first have something worth calling a product.

  1. Transport adapter and normalization — poll only.
  2. Journal, with cursor and ack kept distinct.
  3. Self-echo suppression.
  4. W2: the daemon spawns a handler per batch. You now have a working product.
  5. Heartbeat, single-consumer lock, loud failures.
  6. Coalescing and adaptive backoff.
  7. Filters, and the rules-first answering layer.
  8. W1 and W3 as latency optimizations, if the runtime supports them.
  9. A capability boundary on the handler.

Ship 1–4 before optimizing anything; a correct slow listener beats a fast deaf one.
